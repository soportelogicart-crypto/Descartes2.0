Informe de hosting, API y base de datos

Fecha: 15 de septiembre de 2026 · Destinatarios: equipo Descartes · Alcance: producción y migración a la nube

Este informe resume cómo funciona hoy la producción, dónde se configura cada URL, qué hay que cambiar si la base y la API pasan a un servidor en la nube, y qué tipo de hosting conviene con unos 200 clientes, manteniendo SQL Server o pasando a MySQL.

1. Conclusión recomendada

Seguir con SQL Server y alojar la API y la base en un VPS o servidor cloud (Windows o Linux con SQL Server), no en un hosting web compartido tipo cPanel. La web (Vue) puede seguir en el hosting actual. Pasar a MySQL implicaría reescribir gran parte de la API y migrar los datos de los clientes: más caro y más riesgo que pagar un servidor SQL adecuado.

2. Arquitectura actual de producción

El otro PC no se conecta al SQL ni a la IP de casa. Solo abre la web por HTTPS. El hosting reenvía las llamadas de API al XAMPP de casa, y ese PHP es quien habla con SQL Server.

PC con Electron → https://soportetopay.com/descartes/ (interfaz Vue) → /descartes/api/* (mismo dominio, HTTPS) → proxy.php en el hosting → http://213.96.60.240:9080/descartes-api/public → Apache / PHP en XAMPP de casa → SQL Server local de esa máquina

El router de casa tiene abierto el puerto 9080 (HTTP de la API). El puerto de SQL (1433) no hace falta abrirlo a internet: el SQL solo lo usa PHP en esa misma máquina.

3. Dónde se configura cada cosa

Hay tres sitios distintos. Mezclarlos es el error más habitual.

Qué se apunta Dónde se cambia Valor actual
URL de la aplicación (pantalla) descartes-electron/config.json → appUrl (y el mismo fichero dentro del instalador) https://soportetopay.com/descartes/
Ruta de API que usa el navegador Compilado en el dist (VITE_API_BASE_URL=/descartes) https://soportetopay.com/descartes/api/...
URL/IP real de la API PHP descartes-gestion/public/proxy.php (línea $backend). El de dist/ es una copia del build que se sube al hosting. http://213.96.60.240:9080/descartes-api/public
Servidor SQL (host, base, usuario) Formulario Instalación de Descartes. Se guarda en la API (var/instalacion.json del XAMPP que atiende). Máquina local / red de casa (no es una URL web)
Si se edita solo dist/proxy.php y luego se hace npm run build, el cambio se pierde: hay que modificar public/proxy.php, generar el build y volver a subir proxy.php al hosting.

4. Formulario de instalación: no es la URL de la API

La opción «Base de datos en la nube» sirve para el host de SQL Server (por ejemplo mi-servidor.database.windows.net), más nombre de base, usuario y contraseña. Activa cifrado típico de Azure/SQL en la nube. No es el sitio para poner soportetopay.com ni la IP del proxy.php.

Escenario proxy.php ($backend) Formulario Instalación
Hoy: API y SQL en casa IP pública de casa, puerto 9080 Servidor local / red (nombre de esa máquina)
SQL en la nube, API sigue en casa No se toca «Base de datos en la nube» + host SQL
API y SQL en el mismo servidor cloud URL de esa API PHP Local / red → localhost o nombre de esa máquina
API en un hosting y SQL en otro (p. ej. Azure SQL) URL de la API PHP «Base de datos en la nube» + host SQL

Si API y SQL van en la misma máquina en la nube, es el esquema más simple: PHP se conecta a localhost. Eso no equivale al hosting actual de la web (soportetopay.com), que hoy solo sirve el frontend y el proxy.

5. Por qué un hosting web «normal» no sirve para API + SQL

Descartes usa SQL Server y el driver PHP sqlsrv. Un hosting compartido típico (cPanel, Linux, MySQL/MariaDB, 5–15 €/mes) ofrece:

  • Un sitio web y pocas bases MySQL (a menudo 1–20, según tarifa).
  • Casi nunca SQL Server ni extensión sqlsrv.
  • Límites de CPU, procesos PHP y conexiones insuficientes para un TPV/ERP.

Ese tipo de hosting sí puede seguir sirviendo la interfaz (como ahora). La API y la base deben ir en un servidor donde se instale PHP con sqlsrv y SQL Server.

6. SQL Server o MySQL

Toda la API está escrita en T-SQL de SQL Server: TOP, GETDATE(), IDENTITY_INSERT, ISNULL, esquema dbo, driver sqlsrv, y las bases de los clientes actuales ya son SQL Server (legado Abacus/Descartes).

Seguir con SQL Server Pasar a MySQL
Trabajo de software Ninguno de reescritura. Solo desplegar en el servidor nuevo. Reescribir consultas, migraciones e instalación; meses de trabajo.
Datos de clientes Se copian o se apuntan al mismo motor. Migración de esquema y datos; riesgo de decimales, fechas y collations.
Coste de hosting VPS / cloud algo más caro que MySQL compartido. Hosting más barato, pero el desarrollo sale mucho más caro.
Recomendación Sí, para Descartes 2.0 Solo tendría sentido en un producto nuevo, partido de cero.
Con ~200 clientes, el coste de reescribir y migrar supera con claridad el sobrecoste de un VPS o Azure SQL. No cambiar de motor ahora.

7. Cómo plantear los ~200 clientes

Doscientos clientes no son 200 hostings ni 200 bases en un plan compartido.

  • Un Descartes (SaaS, lo más razonable): una API + un SQL Server. Los clientes se separan por empresa dentro de la misma aplicación, como ya hace el producto. Es lo más barato de operar y de copiar.
  • Una base por cliente: solo si hace falta aislamiento fuerte (contratos, copias independientes). Entonces: una instancia SQL con muchas bases en el mismo VPS, no 200 paneles de hosting.

SQL Server Express es gratuito, pero limita a unos 10 GB por base y poca RAM para el motor (~1,4 GB). Vale para empezar o para tiendas pequeñas. Con 200 establecimientos activos y varios TPV a la vez se quedará corto: hará falta Standard, Azure SQL o un servidor bien dimensionado.

8. Opciones de hosting y coste orientativo

Precios de mercado UE, 2026, sin IVA; varían según proveedor (Hetzner, OVH, Azure, AWS, etc.).

Opción Encaje Coste mensual orientativo
Hosting compartido (cPanel + MySQL) Solo la web Vue. No para API + SQL Server. 5–15 €
VPS con SQL Server Express Arranque, bases < 10 GB, pocos TPV simultáneos. 30–80 €
VPS / dedicado con SQL Standard o Azure SQL Objetivo para ~200 clientes reales. 100–300 € o más, según CPU/RAM y licencia
Web en soportetopay.com + API/SQL en VPS Misma arquitectura de hoy, cambiando solo $backend. Hosting web barato + coste del VPS

Un VPS Windows o Linux con SQL Server (8 o más vCPU, 16–32 GB RAM, disco SSD) es el punto de partida serio. Azure SQL o un elastic pool encajan si se prefiere que Microsoft gestione copias, parches y alta disponibilidad.

9. Arquitectura objetivo (cuando la base esté en la nube)

Lo más simple y coherente con el producto:

Pieza Dónde
Interfaz (Vue / Electron) Puede seguir en soportetopay.com/descartes/
API (PHP + sqlsrv) El mismo servidor cloud que el SQL
SQL Server Ese mismo servidor → en Instalación: local / red, localhost
proxy.php → $backend URL HTTP/HTTPS de esa API (no el nombre del SQL ni la URL de la web)

Si más adelante la API se publica en el mismo dominio que la web, se podría dejar de usar el proxy. Hasta entonces, proxy.php sigue siendo el puente HTTPS → API.

10. Pasos cuando exista el servidor nuevo

  1. Instalar PHP (con sqlsrv), Apache o equivalente, y SQL Server en el VPS/cloud.
  2. Copiar la API (descartes-api) y configurar Instalación con el SQL de esa máquina.
  3. Abrir solo el puerto de la API (HTTPS preferible); no exponer 1433 a internet.
  4. Cambiar $backend en public/proxy.php, hacer build y subir proxy.php al hosting de la web.
  5. Probar login, un TPV y un documento de venta/compra antes de cortar el XAMPP de casa.
  6. Plan de copias: SQL diario + retención; el hosting de la web no sustituye el backup de la base.

11. Resumen para decisión de equipo

  • Motor de datos: SQL Server. No migrar a MySQL en Descartes 2.0.
  • Hosting de la web: compartido actual, válido.
  • Hosting de API + SQL: VPS o cloud con SQL Server, no hosting “normal”.
  • 200 clientes: una API y un SQL (separación por empresa), salvo requisito legal de bases aisladas.
  • URL de la API: proxy.php. Host SQL: formulario Instalación.
